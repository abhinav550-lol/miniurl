# Services

The MiniURL application follows a **microservices architecture**, where each service is responsible for a single business capability. Services communicate through REST APIs behind an API Gateway, allowing them to be developed, deployed, and scaled independently.

---

# 1. User Management Service

## Responsibility

The User Management is responsible for user identity and access management. It handles user registration, login, password security, and JWT token generation. It does **not** manage shortened URLs or perform URL redirections.
Later, will be used for analytics 


## Responsibilities

* Register new users.
* Authenticate existing users.
* Hash passwords using bcrypt.
* Generate Access Tokens and Refresh Tokens.
* Validate JWTs for authenticated requests.
* Refresh expired access tokens.
* Allow users to log out by invalidating refresh tokens (optional implementation).


## Owns

* User accounts
* Password hashes
* Refresh tokens (if stored)
* User information about their managed short URLs and analytics

## Does NOT Handle

* URL generation
* URL redirection
* Analytics

---

# 2. URL Generation Service

## Responsibility

The URL Generation Service is responsible for creating and managing shortened URLs. It validates incoming URLs, generates unique short codes, supports custom aliases, and stores URL mappings.

## Responsibilities

* Validate submitted URLs.
* Generate unique short URLs.
* Accept optional custom aliases.
* Reject duplicate aliases.
* Store mappings between short URLs and original URLs.
* Allow authenticated users to view, edit, and delete their URLs.
* Ensure every generated short URL is globally unique.

## Owns

* URL mappings
* Custom aliases
* URL metadata
* URL ownership information

## Does NOT Handle

* User authentication
* URL redirection
* Analytics

---

# 3. URL Redirection Service

## Responsibility

The URL Redirection Service is responsible for resolving short URLs and redirecting users to their original destinations. Since every visitor accessing a shortened link passes through this service, it is optimized for low latency.

To reduce database queries, the service first checks **Memcached** for the URL mapping. If the mapping is found, the user is redirected immediately. Otherwise, the service retrieves the mapping from PostgreSQL, stores it in Memcached for future requests, and then performs the redirect.

## Responsibilities

* Accept incoming short URL requests.
* Resolve short codes to their original URLs.
* Check Memcached before querying PostgreSQL.
* Cache frequently accessed URL mappings in Memcached.
* Redirect users using HTTP 301 or HTTP 302 responses.
* Display an appropriate error page for invalid or expired links.
* Record click events for future analytics (V2).

## Owns

* URL resolution logic
* Cache interaction
* Redirect responses
* Track analystics, click count and timestamp for visulization month by month and year by year

## Does NOT Handle

* User authentication
* URL creation
* URL editing

---

# Service Communication

The services communicate through REST APIs behind an API Gateway.

Typical request flow:

1. A user registers or logs in through the **Authentication Service**.
2. After receiving a valid JWT, the user interacts with the **URL Generation Service** to create or manage shortened URLs.
3. When anyone visits a shortened link, the request is routed to the **URL Redirection Service**, which first checks **Memcached** for the URL mapping. On a cache miss, it retrieves the mapping from PostgreSQL, stores it in Memcached, and redirects the user.

Each service has a single, well-defined responsibility, making the system easier to maintain, test, and scale independently.
